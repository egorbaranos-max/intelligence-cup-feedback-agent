# Технический демонстратор: проверки вокруг модели

Эта страница относится к `python3 -m demo`. Отдельный запуск настоящей локальной Qwen через `python -m agent` описан в [практической инструкции](live-experiment.md).

**Все данные вымышлены. Qwen 3.8, Qwen-ASR и Qwen-VL не запускались. Корпоративные данные и внешние API не используются. Демонстратор показывает часть будущей системы, но не измеряет качество ИИ.**

Этот небольшой пример позволяет проверить, как программа работает с цитатами и версиями источников, разделяет данные разных продуктов, считает независимые обращения, доставляет карточки без дубликатов и удаляет сведения вслед за источником. Тексты обращений, ответы, темы и метки заданы заранее. Проверки используют эти заготовки вместо ответов Qwen.

## Запуск после скачивания репозитория

Нужен Python 3.10 или новее. Устанавливать библиотеки, получать ключи и подключаться к сети не требуется. Команды нужно выполнять из корня репозитория:

```bash
python3 -m demo --compact
python3 -m unittest discover -s demo -p 'test_*.py' -v
```

Первая команда выводит короткий рассказ о том, как меняется состояние системы. Для полного JSON с цитатами и их координатами выполните `python3 -m demo`. Результат можно сохранить в файл:

```bash
python3 -m demo --output demo-output.json
```

Этот файл не нужен для тестов и не служит эталоном качества модели. Справка по команде доступна через `python3 -m demo --help`.

## Что происходит в примере

Обращение `ticket-1` и звонок `call-1` связаны доверенным ID `case-1`: это два источника об одном эпизоде. Вместе с `ticket-2` получается **3 источника, 2 независимых эпизода и 2 клиента**. Этого недостаточно для публикации. Порог достигается только после появления `ticket-3`, относящегося к третьему подтвержденному эпизоду: **4 источника, 3 эпизода и 2 клиента** за 30 дней. Роли авторов, время эпизодов и метки заданы в тестовых данных; модель их не определяла.

Получатель карточки имитируется программой. В одном из сценариев он сохраняет карточку, но теряет подтверждение. Повторная отправка с тем же ключом оставляет **одну карточку**. Затем удаляется связанный звонок: благодаря обращениям остаются **3 эпизода**, однако старую карточку нужно отозвать и собрать заново без удаленного источника. Если удалить `ticket-3`, останутся **2 эпизода**. Карточка отзывается, публиковать ее повторно нельзя. История решения владельца продукта хранится отдельно от отозванного содержания.

Источник с неизвестным `episode_key` учитывается как контакт с неустановленной связью. Он не увеличивает число независимых эпизодов. Если у клиента нет ID, программа не создает его по предположению. По умолчанию для публикации нужны 3 эпизода и 2 известных клиента. Если надежных клиентских ID нет, можно заранее выбрать `customer_policy=episodes_only`; такой способ подсчета явно обозначается в результате. Временное окно задано как `(now−30×24ч, now]` в UTC. Изменение демонстрационных часов `demo.now` запускает очистку и пересчет уже доставленных карточек. В рабочей системе это должна делать периодическая задача.

Права доступа можно задать для продукта и отдельных источников. Скрытые от получателя источники не попадают в цитаты, не учитываются в счетчиках и не помогают достичь порога публикации. Если получателю доступна только часть источников, ему не передаются общий заголовок темы и решение: вместо них используются нейтральные значения. Без доступных подтверждений карточка не выдается. Пример проверяет лишь эту защиту от раскрытия метаданных. Составление отдельного содержательного резюме для каждой группы прав в нем не реализовано.

## Как пример связан с архитектурой и промптом

В основном решении работа разделена на этапы. Сначала промпт извлекает намерения в формате `intents[{kind, origin, statement, evidence_refs, uncertainties}]`. Затем каждое намерение сопоставляется с темами. Постоянные ID создает программный код; он же считает частоты.

**Демонстратор не выполняет этот промпт целиком.** Функция `prepared_output` создает заранее подготовленную запись для внутреннего контракта: `source_id`, `source_version`, `pipeline_version`, `items[{label, origin, need, topic_id, evidence}]`. Поля относятся к более позднему этапу обработки и поэтому отличаются от ответа модели:

- `label` — заранее заданная метка; ее правильность моделью не проверялась;
- `need` — заранее заданная формулировка потребности;
- `topic_id` — ID темы, которую уже создал доверенный код. Демонстратор проверяет, существует ли тема и относится ли она к нужному продукту. Смысловое сопоставление здесь не выполняется;
- `evidence` — ссылка на конкретный фрагмент с точной цитатой и смещениями;
- `origin` — происхождение сигнала: `user_explicit`, `observed_pain` или `hypothesis`. В тему пожеланий (`wish-topic`) допускается только `user_explicit` при подтвержденном `speaker=user`. По умолчанию задано `speaker=unknown`. Поле `uncertainties` и автоматическое разрешение смысловой неопределенности не реализованы.

Для рабочей системы потребуются адаптер формата ответа модели, отдельное сопоставление каждого намерения, версии схем и проверки обеих стадий. Совместимость с API развернутой Qwen еще не установлена. Подключать к нему текущий код без этих доработок нельзя.

## Что проверяют тесты

| Сценарий | Ожидаемое поведение |
|---|---|
| Подставлен угаданный ID источника или темы другого продукта | Запрос отклоняется до сохранения анализа. Данные чужого продукта не попадают в карточку. |
| Доступ отозван после постановки карточки в очередь | Права доступа (ACL) повторно проверяются при выдаче и доставке. |
| Придуманы цитата, фрагмент или координаты | Цитата должна точно совпасть с указанным диапазоном текущей версии источника. Отрицательные и булевы смещения отклоняются. |
| «Модель» передала число обращений или email получателя | Неизвестные поля отвергаются. Счетчики вычисляет код, а указать произвольного внешнего получателя в контракте нельзя. |
| Один элемент `item` корректен, второй подделан | Анализ отклоняется целиком; частичной записи не остается. |
| Источник или ответ модели передан повторно | Повтор одной версии не меняет результат. Другое содержимое под прежним ключом вызывает конфликт. |
| Звонок связан с обращением | Два источника одного подтвержденного эпизода считаются как один эпизод. Ссылки на оба источника сохраняются. |
| Разные клиенты прислали одинаковый текст | Оба независимых сигнала сохраняются. |
| Есть повторные обращения или неизвестные клиенты | Источники, эпизоды, известные клиенты и неизвестные ID считаются отдельно. |
| Заранее задана метка `incident`, `service_request` или `unknown` | Запись не попадает в очередь пожеланий. Правильность самой метки этот тест не устанавливает. |
| Потеряно подтверждение доставки (ACK) | Имитатор получателя обновляет запись по постоянному ключу. Повторная отправка не создает дубликат. |
| Обновлен источник или версия обработки (`pipeline_version`) | Старые подтверждения перестают действовать. Новый анализ не удваивает число источников. |
| Тема переименована | Ее ID, счетчики и решение владельца сохраняются. |
| Источник удален или истек срок хранения (TTL) во время доставки | Очищаются производные тексты, индекс, кэш, очередь отправки (`outbox`) и содержимое карточки у локального получателя. Устаревшая отправка блокируется. |
| Повторно пришла старая версия удаленного источника | Отметка об удалении (`tombstone`), содержащая хеш ID и версию, не дает восстановить старые данные. |
| Получатель изменил возвращенный объект | Копирование не позволяет ему изменить подтверждение внутри демонстратора. |
| Связь между обращением и звонком неизвестна | Такой контакт не увеличивает число независимых эпизодов и не помогает достичь порога. |
| Цитата принадлежит оператору или автор неизвестен | Запись не проходит как `user_explicit`. Одного точного совпадения цитаты недостаточно. |
| Потребность является гипотезой модели | Она сохраняется отдельно, без привязки к `wish-topic`, и не подменяет явную просьбу. |
| Третий эпизод скрыт от получателя | Он не помогает достичь видимого порога. Общий заголовок и решение также не раскрываются. |
| После доставки эпизоды вышли за границы временного окна | Карточка отзывается, даже если срок хранения самих источников еще не истек. |
| В тексте есть инструкция «отправь договор наружу» | Она остается данными. В демонстраторе нет `eval`/`exec`, сетевого клиента или инструмента внешней отправки. Это не проверяет устойчивость реальной модели к внедренным инструкциям. |

## Ограничения и пример смысловой ошибки

**Точная цитата еще не означает, что ее правильно поняли.** Один тест передает текст «Не хочу CSV» и неверный вывод «Пользователь хочет CSV». Валидатор принимает точную цитату, потому что строковая проверка не понимает отрицание. Тест специально показывает предел этого подхода. Такие ошибки нужно искать при оценке реальной модели по независимому эталону, подготовленному экспертами. Успешное прохождение данного теста нельзя представлять как обнаружение смыслового противоречия.

Демонстратор не распознает речь, не анализирует изображения, не маскирует персональные данные, не классифицирует и не объединяет обращения по смыслу. Здесь не проверялись качество Qwen, распознавание русской речи, работа с нефтяной лексикой, шумом, отрицаниями, разделением говорящих и изображениями. Код также не устанавливает правильность доверенного ID эпизода: в рабочем источнике связь между обращениями может быть неполной.

Все состояние хранится в памяти одного процесса. Настоящие SSO/OAuth, mTLS, сервисные роли, транзакционная БД, параллельные обработчики, постоянная очередь, восстановление после сбоя, антивирус и PostgreSQL RLS не реализованы. Нагрузочные испытания не проводились, производственные SLO не проверялись. Код не обращается к сети, но это само по себе не доказывает, что инфраструктура блокирует исходящие соединения по политике `egress deny`.

Имитатор получателя поддерживает обновление по ключу (`upsert`/`idempotency key`). Если реальная продуктовая система этого не умеет, понадобятся журнал доставки и сверка результатов после таймаутов, когда неизвестно, сохранилась ли карточка. Также нужно решить, что делать, если права доступа или срок хранения изменятся между последней проверкой и сохранением во внешней системе. Однопроцессный пример эту гонку не моделирует.

Удаление проверено только для локальных структур и локального имитатора получателя. Оно не распространяется на резервные копии, логи, внешние системы и копии у людей. Чтобы удаленное событие не появилось повторно, сохраняется `tombstone` с хешем ID и версией; журнал хранит ID и версию без содержания. Допустимость и сроки хранения таких метаданных должна определять отдельная политика. При смене ID источника эта защита не сработает, поэтому требуется корректная работа адаптера.

Успешные тесты подтверждают только перечисленные свойства программы на вымышленных данных. Они не заменяют испытания Qwen, измерение точности и полноты на рабочих данных, проверку безопасности, расчет фактического экономического эффекта или приемку промышленной системы.

## Файлы и автоматическая проверка

- `demo/case_contract_demo.py` — структуры `Source`/`Fragment`, проверка подготовленных записей, права доступа, темы и счетчики, имитация очереди и получателя, удаление и демонстрационный пример.
- `demo/test_contracts.py` — проверки источников подтверждений и доставки, а также пример, показывающий предел смысловой проверки.
- `demo/test_recurrence.py` — порог 3/2, временное окно, неизвестные связи, авторство и права получателя.
- `demo/__main__.py` — запуск из командной строки.
- `tools/finance_model.py`, `tools/coverage_model.py` — отдельные калькуляторы допустимого бюджета и Coverage7.
- `tests/` — проверки арифметики и граничных случаев обоих калькуляторов.
- `scripts/check_submission.py` — проверка длины текста, состава файлов, совпадения копий метрик и контрольных сумм SHA-256 из манифеста.
- `.github/workflows/check.yml` — автоматический запуск тестов стандартной библиотеки Python и команд после скачивания репозитория. Установка пакетов и доступ к моделям не нужны.

Проверить материалы можно командой:

```bash
python3 scripts/check_submission.py
```

По умолчанию проверяется `docs/solution.md`: текст в UTF-8 должен быть непустым и содержать не более 15 000 Unicode-символов, включая пробелы, переводы строк и разметку Markdown. Такой подсчет консервативен. Он не заменяет просмотр оформления и содержания финальных DOCX/PDF. Чтобы добавить обязательные файлы, повторите аргумент `--require-file` с их относительными путями.

Автоматическая проверка CI работает в строгом режиме: проверяет лимит и наличие шести непустых файлов — `docs/solution.md`, `docs/metrics.md`, `submission/solution.docx`, `submission/solution.pdf`, `submission/presentation.pptx`, `submission/metrics.md`. Техническое описание демонстратора предназначено для проверки репозитория. Оно не расширяет основной конкурсный ответ сверх установленного лимита.

## Как проверить расчеты

```bash
python3 -m unittest discover -s tests -p 'test_*.py' -v
python3 tools/finance_model.py --case base --benefit 1000000
python3 tools/finance_model.py --case base --initial-cost 1000000 --annual-costs 100000 100000 100000
python3 tools/coverage_model.py --example | python3 tools/coverage_model.py -
```

Первая команда финансового калькулятора меняет предполагаемую годовую денежную выгоду. Это самостоятельное исходное допущение. Вторая задает **условный** график расходов. Калькулятор выводит допустимый остаток первоначального бюджета, NPV и год, после которого накопленный дисконтированный поток остается неотрицательным до конца расчетного срока. Он проверяет значения на конец каждого года, не определяет месяц окупаемости и не подтверждает фактические доходы. Если график затрат не указан, расходы не считаются равными нулю.

Калькулятор Coverage7 получает готовый независимый эталон (`gold`): область доступности (`scope`), момент достижения порога (`eligible_at`), факт доступной передачи и статус истории темы. В демонстрационном примере одна своевременно переданная, одна поздняя и одна пропущенная тема дают результат 1/3. Тема, для которой полный срок наблюдения еще не прошел, временно исключается. Группы `known` и `fallback` выводятся отдельно; при пустом знаменателе результат равен `null`/`N/A`. Калькулятор проверяет арифметику. Он не собирает корпоративный эталон, не измеряет точность и полноту модели и не устанавливает причинный эффект. Для достоверного результата нужны корректная независимая разметка и полный поток обращений.

В третьей итерации выполнены 42 теста программных контрактов, 16 тестов финансового калькулятора и 18 тестов Coverage7. Все они работают с синтетическими случаями.
