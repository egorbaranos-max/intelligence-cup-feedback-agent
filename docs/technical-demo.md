# Технический демонстратор: программные контракты

**Синтетические данные. Qwen 3.8, Qwen-ASR и Qwen-VL не запускались. Корпоративных данных и внешних API нет. Демонстратор не является готовым ИИ-агентом и не измеряет его точность.**

Задача этой небольшой реализации — показать проверяемую программную обвязку вокруг будущей модели: валидацию цитат и версий, разграничение продуктовых областей, независимые счетчики, идемпотентную доставку и очистку после удаления источника. Все примеры обращений и подготовленных ответов вымышлены. Решения о темах/метках в примере написаны человеком, а не получены от нейросети.

## Запуск из чистого checkout

Нужен Python 3.10 или новее. Установка библиотек, ключи, подключение моделей и сеть не требуются. Выполнять из корня репозитория:

```bash
python3 -m demo --compact
python3 -m unittest discover -s demo -p 'test_*.py' -v
```

Первая команда печатает короткую цепочку состояний. Полный JSON с цитатами и координатами: `python3 -m demo`. Чтобы сохранить результат:

```bash
python3 -m demo --output demo-output.json
```

Файл результата не нужен для запуска тестов и не является эталоном качества модели. У CLI есть справка: `python3 -m demo --help`.

## Что показывает пример

Тикет `ticket-1` и звонок `call-1` имеют доверенный ID `case-1`. Вместе с `ticket-2` это **3 источника, 2 независимых эпизода, 2 клиента**. Публикация блокируется. Только `ticket-3` с третьим подтвержденным эпизодом достигает порога: **4 источника → 3 эпизода / 2 клиента** за 30 дней. Все роли авторов, время эпизодов и метки заданы синтетическими fixtures, а не распознаны моделью.

Мок получателя теряет подтверждение сохранения. Повтор по ключу оставляет **одну карточку**. Удаление связанного звонка сохраняет **3 эпизода** за счет тикетов, но отзывает старую версию карточки до пересборки. Удаление `ticket-3` оставляет **2 эпизода**: карточка отзывается, повторная публикация блокируется. История решения PM хранится отдельно от отозванного содержания.

Неизвестный episode_key считается отдельным неразрешенным контактом, а не независимым эпизодом. Клиенты без ID не придумываются. По умолчанию нужны 3 эпизода и 2 известных клиента; заранее выбранный `customer_policy=episodes_only` явно маркирует запасной эпизодный вариант. Окно имеет границу `(now−30×24ч, now]` в UTC. Изменение демонстрационных часов `demo.now` запускает очистку и пересчет уже доставленных карточек; рабочей системе нужен периодический reconciler.

Права можно ограничить продуктом и конкретными источниками. Скрытые источники не влияют на цитаты, счетчики и порог получателя. Для ограниченного источниками view глобальный заголовок/решение не копируются, используются нейтральные значения; без доступных evidence карточка не выдается. Это ограниченный мок защиты метаданных, не генерация полного смыслового резюме для каждой области прав.

## Связь с архитектурой и системным промптом

Основное решение предусматривает отдельные этапы: extraction-only промпт извлекает `intents[{kind, origin, statement, evidence_refs, uncertainties}]`; затем выполняется сопоставление каждого намерения с темами, а программный код создает стабильные ID и считает частоты.

**Демонстратор не реализует этот промпт целиком.** Его `prepared_output` формирует заранее подготовленную нормализованную запись для внутреннего программного контракта: `source_id`, `source_version`, `pipeline_version`, `items[{label, origin, need, topic_id, evidence}]`. Различие имен полей и стадий намеренно:

- `label` — уже подготовленная метка, а не результат испытанной классификации;
- `need` — вручную написанная потребность;
- `topic_id` — ID темы, заранее созданной доверенным кодом; демонстратор проверяет ее существование/продуктовую область, но не выполняет смысловой matching;
- `evidence` — проверяемая ссылка на конкретный фрагмент с точной цитатой и смещениями;
- `origin` отделяет user_explicit, observed_pain и hypothesis; в wish-topic допускается только user_explicit с подтвержденным speaker=user. По умолчанию speaker=unknown. Поле uncertainties и автоматическое смысловое разрешение неопределенности здесь не реализованы.

В промышленной реализации понадобятся явный адаптер extraction-контракта, отдельный per-intent matching, версии схем и проверки обеих стадий. Текущий код не доказывает совместимость с API развернутой Qwen и не должен подключаться к нему без этих доработок.

## Что проверяют контрактные тесты

| Группа сценариев | Инвариант |
|---|---|
| Угаданные ID источника/темы другого продукта | Запрос отклоняется до записи анализа; чужой продукт не попадает в карточку. |
| Отзыв доступа после постановки в очередь | ACL повторно проверяется на выдаче и доставке. |
| Придуманная цитата, фрагмент или координаты | Точная цитата должна совпасть с указанным диапазоном текущего источника; отрицательные и булевы смещения отклоняются. |
| Число обращений/email от «модели» | Неизвестные поля отвергаются; счетчики вычисляет код; произвольного внешнего получателя в контракте нет. |
| Один валидный и один поддельный item | Не остается частичной записи анализа. |
| Повтор source/model output | Версии идемпотентны; изменение содержимого под прежним ключом — конфликт. |
| Звонок + связанный тикет | Два источника одного подтвержденного эпизода дают один независимый эпизод и отдельные provenance. |
| Одинаковый текст разных клиентов | Два независимых сигнала сохраняются. |
| Повторные обращения/неизвестный клиент | Отдельно считаются источники, эпизоды, известные клиенты и неизвестные ID. |
| Известная метка incident/service_request/unknown | Не попадает в очередь пожеланий; правильность самой метки не определяется. |
| Потерянный ACK | Мок получателя обновляет по стабильному ключу, повтор не размножает карточки. |
| Обновление/новая pipeline version | Старые доказательства инвалидируются; новая версия анализа не удваивает источник. |
| Переименование темы | ID, счетчики и решение владельца сохраняются. |
| Удаление/TTL в момент доставки | Очищаются производные тексты, индекс, кэш, outbox и payload локального мока; устаревшая отправка блокируется. |
| Запоздалый replay удаленного источника | Tombstone хеш ID/версия блокирует воскрешение старой версии. |
| Изменение возвращенного объекта | Копирование не позволяет потребителю испортить внутреннее доказательство. |
| Неизвестная связь тикета и звонка | Не увеличивает число независимых эпизодов и не выполняет порог. |
| Роль оператора или неизвестный автор | Не проходит как user_explicit; точная цитата сама по себе недостаточна. |
| Гипотеза модели | Сохраняется отдельно без wish-topic, не подменяет явную просьбу. |
| Скрытый третий эпизод | Не дополняет видимый порог; глобальный заголовок/решение не раскрывается. |
| Старение окна после доставки | Устаревшая текущая карточка отзывается даже при живом TTL источников. |
| Инструкция «отправь договор наружу» внутри текста | Остается данными; у демонстратора нет eval/exec, сетевого клиента или tool внешней отправки. Это не тест injection-устойчивости реальной LLM. |

## Ограничения и намеренно показанный отрицательный пример

**Точная цитата не подтверждает правильность смысла.** Один тест передает текст «Не хочу CSV» и неверное утверждение «Пользователь хочет CSV». Валидатор принимает точную цитату: строковая проверка не понимает отрицание. Это зафиксированный предел программного контракта. Ошибку должен выявлять независимый человеческий эталон и оценка реальной модели; успешный тест нельзя представлять как обнаружение смыслового противоречия.

Демонстратор не распознает речь, не анализирует изображения, не маскирует персональные данные и не классифицирует/кластеризует по смыслу. Качество Qwen, русского ASR, нефтяной лексики, шума, отрицаний, диаризации и изображения здесь не проверялось. Правильность доверенного ID эпизода также не установлена этим кодом: в рабочем источнике такая связь может быть неполной.

Состояние — память одного процесса. Здесь нет настоящих SSO/OAuth, mTLS, сервисных ролей, транзакционной БД, конкурентных обработчиков, долговечной очереди, crash recovery, антивируса, PostgreSQL RLS, нагрузочного теста или производственных SLO. Сеть не используется кодом, но инфраструктурная политика egress deny этим запуском не доказывается.

Мок получателя поддерживает upsert/idempotency key. Если реальная продуктовая система не поддерживает такой контракт, нужны журнал доставки и сверка неоднозначных таймаутов. Гонка между последней проверкой ACL/TTL и внешней фиксацией также требует производственного решения: однопроцессный пример ее не моделирует.

Удаление доказано для локальных структур и локального мока. Каскадное удаление в резервных копиях, логах, внешних системах и у людей не реализовано. Против повторного появления удаленного события сохраняется tombstone хеш ID/версия; журнал хранит ID/версию без содержания. Разрешенность и сроки хранения таких метаданных должны задаваться отдельной политикой. Смена ID источника обходила бы такой tombstone; корректность адаптера остается предпосылкой.

Успешные тесты подтверждают только перечисленные программные инварианты на синтетике. Это **не испытания Qwen**, не production precision/recall, не доказательство безопасности или экономического эффекта и не приемка промышленного релиза.

## Структура файлов и CI

- `demo/case_contract_demo.py`: Source/Fragment, валидация нормализованных fixtures, ACL, темы/счетчики, mock outbox/receiver, удаление и пример.
- `demo/test_contracts.py`: проверки происхождения/доставки и предел смысловой проверки на одиночных fixtures.
- `demo/test_recurrence.py`: порог 3/2, окно, неизвестные связи, авторство и права получателя.
- `demo/__main__.py`: запускаемый модуль CLI.
- `tools/finance_model.py`, `tools/coverage_model.py`: независимые калькуляторы денежного потолка и Coverage7.
- `tests/`: проверки арифметики и граничных случаев двух калькуляторов.
- `scripts/check_submission.py`: длина, комплект, совпадение метрик и SHA-256 манифеста экспортов.
- `.github/workflows/check.yml`: запуск stdlib-тестов и CLI из checkout без установки пакетов/доступа к моделям.

Проверка исходного текста:

```bash
python3 scripts/check_submission.py
```

По умолчанию проверяется `docs/solution.md`: непустой UTF-8 текст длиной не более 15 000 Unicode-символов, включая пробелы, переводы строк и Markdown-разметку. Это консервативная автоматическая проверка исходника; она не заменяет проверку визуального оформления и содержимого финального DOCX/PDF. Для обязательных файлов можно повторить аргумент `--require-file` с их относительными путями.

CI использует строгий режим: проверяет лимит и наличие шести непустых файлов — `docs/solution.md`, `docs/metrics.md`, `submission/solution.docx`, `submission/solution.pdf`, `submission/presentation.pptx`, `submission/metrics.md`. Технический демонстратор — материал репозитория для проверки; он не является приложением, расширяющим лимит конкурсного основного решения.

## Калькуляторы для проверки аргументов

```bash
python3 -m unittest discover -s tests -p 'test_*.py' -v
python3 tools/finance_model.py --case base --benefit 1000000
python3 tools/finance_model.py --case base --initial-cost 1000000 --annual-costs 100000 100000 100000
python3 tools/coverage_model.py --example | python3 tools/coverage_model.py -
```

Первая финансовая команда меняет независимую предполагаемую годовую денежную выгоду; вторая подставляет **условный**, явно заданный график расходов. Калькулятор показывает остаточный предел первоначального бюджета, NPV и устойчивое пересечение нуля по концам лет. Он не доказывает фактические доходы и не оценивает месяц окупаемости. Без явного графика затраты не подставляются равными нулю.

Coverage7 получает уже независимо размеченный gold с scope, eligible_at, фактом доступной передачи и статусом истории. Пример: одна своевременная, одна поздняя и одна пропущенная зрелая тема дают 1/3; незрелая тема исключается до полного срока. Отдельно выводятся known и fallback когорты, пустой знаменатель — null/N/A. Это проверка арифметики, не сбор корпоративного эталона, не измерение precision/recall или причинного эффекта. Наличие корректного gold и полного потока остается внешней предпосылкой.
