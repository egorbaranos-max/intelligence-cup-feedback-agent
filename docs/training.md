# Как улучшать и дообучать агента

Сейчас меняются инструкции, способ извлечения цитат и проверки программы. Сравниваются размеры локальной модели. **Это не дообучение весов.** Непроверенные ответы самой модели не используются как правильные учебные ответы.

## Что можно сделать вашей команде

В [пакете разметки](../team/annotation-pack/index.html) есть 35 старых проверочных обращений. Откройте `index.html` из скачанного репозитория на компьютере. Страница не использует внешние библиотеки и не отправляет данные в интернет. На GitHub HTML показывается как исходный файл; для работы нужна локальная копия.

1. Два участника независимо читают каждое обращение. До первого прохода не смотрят ответы агента и разметку друг друга.
2. Указывают смысл: новая функция, обычная операция, неисправность, неудобство или недостаток сведений. Одно обращение может содержать несколько намерений. Отрицание потребности и команда выдумать спрос не являются пожеланием.
3. Для каждого намерения выбирают исходные фрагменты, подтверждающие именно его. Отмечают неопределенности и проверенный статус автора; недостающие сведения не придумывают.
4. Указывают семейство похожих примеров и часть данных: `train` для обучения, `valid` для выбора настроек, `test` для последней проверки. Все перефразировки, дубли и связанные эпизоды одного семейства должны остаться в одной части.
5. Сохраняют два JSON-файла. Расхождения разбирает третий участник, исходные независимые ответы сохраняются.

Эти 35 примеров уже видели разработчики алгоритма. Даже если люди сейчас их разметят, они **не станут независимым тестом текущего проекта**. Пакет полезен для упражнения и подготовки учебных данных. Для итоговой проверки следующей версии нужна новая отложенная выборка, лучше разрешенные обращения компании. Вымышленные примеры и примеры компании должны быть различимы в отчете.

Поля «человек» и «независимо» — заявления участников, а не подтверждение личности программой. Код проверяет целостность, формат и согласованность; он не способен доказать, что два участника действительно работали независимо или правильно поняли текст.

## Подготовить пакет на своих разрешенных данных

Из корня репозитория, Python 3.10+:

```bash
python3 tools/annotation_workflow.py prepare \
  --inputs artifacts/allowed-inputs.jsonl \
  --output artifacts/human-review-pack
```

Формат исходных обращений описан в [инструкции запуска](live-experiment.md). Все записи останутся неразмеченными: программа не подставляет ответы модели. Созданный `index.html` содержит исходные тексты. Не публикуйте его с настоящими обращениями без разрешения владельца данных.

## Согласовать и экспортировать

```bash
python3 tools/annotation_workflow.py export \
  --inputs artifacts/allowed-inputs.jsonl \
  --reviews artifacts/reviewer-a.json artifacts/reviewer-b.json \
  --output artifacts/training-export-01
```

При разногласиях команда завершится с кодом 2 и перечислит записи. Учебные файлы не создаются. Подготовьте отдельный пакет для третьего участника:

```bash
python3 tools/annotation_workflow.py prepare-adjudication \
  --inputs artifacts/allowed-inputs.jsonl \
  --reviews artifacts/reviewer-a.json artifacts/reviewer-b.json \
  --output artifacts/adjudication-pack
```

Команда принимает только две полные проверенные разметки с разными заявленными участниками и подтверждением независимости. В новом `index.html` показаны только спорные записи и оба исходных ответа. Третий человек может взять любой ответ за основу или заполнить свой, отредактировать его и отдельно отметить запись проверенной. Любая последующая правка снимает эту отметку. Исходные ответы не меняются. При отсутствии расхождений пакет не создается.

Третий участник указывает свой ID, отличный от двух первых, и сам подтверждает человеческую проверку. Независимость первой разметки для согласования не заявляется: `attested_independent` остается `false`. Кнопка скачивания сохраняет JSON с ровно спорными записями и хешем **полного исходного набора**, поэтому вручную удалять лишние записи не нужно. Непроверенные решения остаются черновиком и блокируют экспорт. Пустой список намерений допустим после явной проверки.

Добавьте `--adjudication artifacts/adjudication.json` к команде экспорта. Для `--inputs` снова используйте полный исходный файл `artifacts/allowed-inputs.jsonl`, а не файл спорной подвыборки внутри пакета. Экспортер проверяет, что согласованы ровно все расхождения. Оба независимых ответа и решение третьего участника сохраняйте отдельно. При восстановлении поврежденного JSON текущий несохраненный черновик остается на месте.

Результат:

- `training/train.jsonl` — примеры обучения извлечению намерений.
- `training/valid.jsonl` — примеры для выбора настроек.
- `heldout/inputs.jsonl` и `heldout/labels.jsonl` — отдельная контрольная часть вне папки обучения.
- `manifest.json` — хеши, заявленные участники, версия кода и ограничения.

Экспорт отказывается молча выбросить сложные записи, принять неподтвержденную цитату или разнести один эпизод по разным частям. Одинаковые формулировки ответа двух людей проверяются строго; допустимые перефразировки тоже могут потребовать третьего решения. Это увеличивает работу, но не скрывает разногласия.

## Когда имеет смысл обучать веса

Сначала исправляем ошибки программы и добавляем проверенный контекст продукта. Если ошибки понимания сохраняются на достаточном количестве размеченных данных, можно испытать адаптер LoRA/QLoRA — небольшую обучаемую добавку к модели. MLX LM поддерживает такой способ обучения локально; форматы и команды описаны в [официальной документации MLX LM](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/LORA.md).

Число примеров само по себе не гарантирует успех. Нужны разные продукты, формулировки, отрицания, редкие классы, примеры с несколькими намерениями и надежно размеченные повторяющиеся темы. Размер набора выбирают по представленности этих случаев и кривой качества. Учебные данные из нашего экспорта относятся только к извлечению намерений: сопоставление тем и проверку доказательств нужно оценивать отдельно.

Перед обучением фиксируют исходную модель, промпт, разделение данных, параметры и критерий выбора. Шаблон диалога и режим thinking при обучении должны совпадать с запуском. Во время обучения настраиваются только по `valid`; окончательный набор `test` открывают после выбора версии. Снижение учебной ошибки не доказывает улучшение карточек.

После обучения сравнивают исходную и новую модели на одинаковых неизученных примерах: ложные пожелания, пропуски, неверные объединения, долю ручного разбора, скорость. Нужен также полный прогон от обращения до карточки. Если стало хуже — адаптер не используют. Даже хороший результат не отменяет проверки доступа, удалений, корпоративных подключений и реального бизнес-эффекта.

**Сейчас подтвержденного дообучения нет.** Есть код подготовки данных, пустые формы для людей, локальные модельные эксперименты и журнал найденных ошибок. Для обучения на данных компании нужны ее разрешение, специалисты и интерфейс внутренней модели. Результаты открытой Qwen нельзя переносить на внутреннюю Qwen из задания.
